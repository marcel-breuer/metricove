# Optional module contract

## Scope
The always-enabled Core owns accounts, household setup, invitation identity, admin status, module states, access permissions and audit. Feature modules are versioned code bundled with the installation; the admin can enable or disable them without discarding existing data.

## Core first-run setup
`GET /api/setup/status` reports only whether first-run setup is available. `POST /api/setup` accepts the first member's display name, normalized email and confirmed password. The database contains one fixed household-settings row; a transaction locks and atomically claims it before creating the first active administrator. The successful response initializes a web session. The endpoint returns `409 Conflict` after setup, and the form is protected by Laravel's session and CSRF middleware. No public account-registration endpoint remains open after this one-time flow.

## Core authentication and member profile
The current Core authentication surface is same-origin and session-based:

- `GET /api/auth/session` returns the signed-in member's public profile or `user: null`; it also initializes the CSRF cookie.
- `POST /api/auth/login` accepts a normalized email and password, regenerates the session on success and rate-limits attempts by IP and normalized email.
- `POST /api/auth/logout` invalidates the session and rotates the CSRF token.
- `GET /api/profile` and `PATCH /api/profile` require an authenticated session. Members can change their display name, email, language (`en` or `de`), number/date locale (`de-DE`, `en-US` or `en-GB`), default currency (`EUR`, `USD`, `GBP` or `CHF`) and currency display (`code` or `symbol`); email uniqueness is case-insensitive and whitespace-normalized in both application validation and the database. Locale and currency preferences are per-member. The currency preference initializes new money-entry forms and never converts existing records.
- `GET /api/profile/mcp`, `POST /api/profile/mcp/tokens` and `DELETE /api/profile/mcp/tokens/{id}` manage the signed-in member's MCP tokens. A token secret is returned only on creation; the database stores its SHA-256 digest. Tokens have member-selected module scopes and can expire within 1–365 days or be created without an expiry (`expires_in_days: null`). They take effect only while the member, module and permissions remain active. Each member can see and revoke only their own tokens.
- `POST /api/auth/password/email` returns the same response for known and unknown addresses. Reset links expire, are throttled per member, and the stored token is hashed. The token is delivered in the URL fragment so it is not sent to the web server in the initial page request; the frontend removes it from the address bar before submitting it to the API.
- `POST /api/auth/password/reset` accepts a valid, unexpired token once and applies the configured minimum password length. Both reset operations are rate-limited by IP.

Session cookies are encrypted, `HttpOnly`, `SameSite=Lax`, and `Secure` when `APP_URL` uses HTTPS unless explicitly overridden. Per-installation SMTP settings deliver reset messages; the default mailer is SMTP, not a log transport, so reset links are not written to application logs. Public registration remains closed after initial setup.

## Core invitations
Only an active household administrator can manage invitations. `POST /api/admin/invitations` accepts a normalized email address only; `GET /api/admin/invitations` lists unclaimed invitations, including expired ones so they can be resent. `POST /api/admin/invitations/{id}/resend` rotates the token and expiry, invalidating any earlier link, and `DELETE /api/admin/invitations/{id}` revokes the invitation.

Invitation tokens are random and stored as SHA-256 digests. They expire after seven days by default (`AUTH_INVITATION_EXPIRE` can override the lifetime in minutes) and are delivered through the installation's configured SMTP mailer. The link carries the token in a URL fragment; the web page removes it from the address bar before posting it to `POST /api/invitations/claim`. Claiming creates an active non-admin account whose normalized email comes only from the invitation record, marks that address verified, accepts the invitation atomically, regenerates the session and signs in the recipient. In the same transaction, the new member receives all four capabilities for each optional module that is enabled at claim time; each automatic grant is audited without email addresses or other profile details. Invalid, expired, revoked, replayed and already-registered claims receive the same generic response. Delivery failures do not log recipient addresses or tokens; the pending invitation remains available for resend.

## Core member administration
`GET /api/admin/members` lists active and suspended members for active administrators. `PATCH /api/admin/members/{id}` accepts only `is_admin` and/or `is_active`; `DELETE /api/admin/members/{id}` removes an account. An administrator may promote, demote, activate, suspend or remove any member, including themselves when another active administrator remains. The API rejects changes that would demote, suspend or remove the final active administrator with `409 Conflict`.

All authenticated API routes require an active member. Suspending an account also invalidates its web session on the next request; it cannot keep using profile or future protected endpoints with an existing cookie.

Every access change and removal is recorded in `household_audit_events` in the same transaction as the member change; no API endpoint edits or deletes audit events. `GET /api/admin/member-audit` returns the latest 100 events. Audit details contain only role/status flags and numeric member IDs, never email addresses, passwords or other profile fields. Member mutations acquire the singleton `household_settings` row lock and recount active administrators inside that transaction; every role/status/removal path must use this service so competing requests cannot remove the final admin.

If an operator must recover an existing account after out-of-band damage, run `php artisan metricove:recover-admin <user-id>` in the API container. This command can reactivate and promote only an existing member and records the recovery in the same audit table. It does not create accounts or expose an HTTP recovery endpoint.

## Core household reminders

`GET /api/reminders` returns up to 100 upcoming reminders for the signed-in member; `PATCH /api/reminders/{id}` accepts `action: read|dismiss`. Reminder source records are resolved live, and the same module capability and resource-visibility checks used by their source modules run before the title or record link is returned. A disabled source module, removed source record, changed due date or revoked resource grant hides and purges the reminder. Administrators do not receive access to another member's private reminders.

`GET/PATCH /api/reminders/preferences` manages the signed-in member's reminder settings: email delivery is off by default, the lead window defaults to 3 days (0–30), and Finance, Vehicles, Utilities and Pantry can each be disabled. `metricove:generate-reminders` runs daily at 08:00 in the application timezone; occurrences are unique by recipient, source record and occurrence key, so reruns do not duplicate inbox entries or email. A pending, unclaimed reminder follows the member's current email preference, so opting in later can send its email on a subsequent generation run. Email is sent synchronously through the installation's SMTP settings. A durable delivery claim is committed before SMTP; ambiguous delivery outcomes are not retried automatically to avoid duplicate emails, so an interrupted attempt may require operator follow-up. The email has a minimal text body and is sent only after current source permissions are rechecked. No source details or recipient addresses are written to application logs.

The initial sources are due Finance recurring entries; Vehicle insurance expiration and maintenance records with an optional `next_due_on`; Pantry best-before dates; and Utilities intervals where the latest two visible readings exceed the meter's configured alert threshold. Utility alerts use exact decimal comparisons and require view access to the meter and both source readings. Personal lead time applies to date-based obligations; utility threshold alerts are generated when detected. The reminder API remains part of Core and does not depend on any optional module being enabled.

## Core module registry and activation

The versioned registry in `apps/api/config/modules.php` defines stable keys, labels, descriptions, versions, required module keys and whether a module is always enabled. `core` is always available and is not stored as an optional state. Optional modules default to disabled until an administrator enables them. The registry rejects missing dependencies, self-dependencies and dependency cycles during application boot. Current optional modules require only Core; optional integrations remain independent, including Recipes, MealPlanning, Pantry and Shopping.

The Core module settings API is:

- `GET /api/admin/modules` returns the registered catalog, enabled state, unmet requirements and enabled dependents to active administrators.
- `PATCH /api/admin/modules/{key}` accepts only `enabled: boolean`. Enabling with an unmet requirement returns `422` and its module keys. Disabling a required module while a dependent is enabled returns `409` and the dependent keys. Disabling Core returns `409`.
- `GET /api/modules` returns household `enabled_modules` and an `available_modules` navigation catalog for the signed-in member. The latter contains only enabled optional modules with at least one exact `view`, `create`, `edit` or `manage` grant, and includes that member's capability flags. Core administration stays separate from optional modules.

Changes lock the singleton `household_settings` row and recheck the administrator from the database. Optional modules default to disabled; an absent state row means disabled, and Core is always returned as enabled. Enabling an optional module writes its state and grants all four capabilities (`view`, `create`, `edit` and `manage`) to every active household member in the same transaction. Each changed member grant is audited. Calling enable again while the module is already enabled does not reset individually narrowed rights. Disabling preserves module data and stored rights; a later re-enable restores all four capabilities for every active member.

Every optional API operation must use `module.access:{key},{capability}` and call `ModuleAccessService::authorize($actor, $key, $capability, $resource)` before accessing a record. This single check requires an active module, an exact member capability and, for private resources, record ownership or an explicit record-level grant. Do not use `module.enabled:{key}` alone for member data operations. User-initiated queue jobs must include `App\Jobs\Middleware\EnsureModuleAccess` with the initiating member ID, module key and capability so access is checked again when the job runs. Typed AI/MCP tools must call the same `ModuleAccessService` with the current member, capability and resource; `ModuleStateService::assertEnabled($key)` alone is insufficient. SvelteKit module navigation must be derived from `GET /api/modules`; navigation is advisory and server checks remain authoritative. Module data surfaces are delivered incrementally; new routes, jobs and tools must follow these gates and add disabled/private-access regression tests.

## Per-member module rights and private records

`module_user_permissions` stores independent `view`, `create`, `edit` and `manage` grants per member and optional module. Before a module is enabled, an absent grant defaults to false. Module activation grants all four capabilities to active members; an active administrator can then narrow them through `GET /api/admin/members/{member}/module-permissions` and `PUT /api/admin/members/{member}/module-permissions/{moduleKey}`. Stored rights remain while a module is disabled, but re-enabling grants all four capabilities again. Manual and automatic changes are audited without email addresses or private record values; initial grants for invited members use a null audit actor to identify system-driven provisioning. There is no separate `delete` capability: delete operations use the existing exact `edit` or `manage` authorization required by that operation. Core permissions continue to use Core account roles and are not editable in this matrix.

Administrator status grants access to member and module administration only. It does not grant optional-module capabilities or access to another member's private records. `manage` is an exact module capability; it does not imply `view`, `create`, `edit` or private-record access.

Any module model used in an authorization decision must implement `App\Contracts\ModuleResource` and declare its module key, nullable owner user ID and private/shared state. A private record must have an owner. The owner must still hold the required module capability. Another member, including an administrator, must hold both that module capability and an explicit `resource_user_permissions` grant for the exact record and operation. Only the active record owner with module-level `manage` permission may issue or revoke those grants. Models with persisted resource grants must use `App\Models\Concerns\HasResourcePermissions` so deleting a record removes its grants. Shared records still require the member's exact module capability.

The UI presents capability checkboxes per member and module and uses shared Svelte controls for fields, notices, buttons, panels, switches and page headings. The theme preference can follow the browser or be set to Light or Dark; it is stored in that browser. The authenticated app shell uses `available_modules` for responsive navigation and uses the same API state for module links; hidden navigation does not authorize operations. REST, jobs and AI/MCP must call `ModuleAccessService` at the operation boundary. A resource that does not declare its ownership policy fails closed when passed to that service.

The interface language is stored per member as English (`en`) or German (`de`) and returned by the session and profile APIs. The current translation catalog covers the authenticated shell, dashboard, sign-in, profile and MCP reference; untranslated module text falls back to its English source copy. Number/date formatting is independently selected per member. Numeric and date rendering follows the chosen locale; currency display can use ISO codes or localized symbols. Stored amounts and currency codes remain unchanged. New finance and vehicle-cost forms use the member's default currency; editing an existing record keeps its stored currency.

Numeric display formatting is presentation-only. Currency amounts keep two decimal places, vehicle distances in km/mi show at most one, and other measurements show at most three with insignificant trailing zeros removed. A non-zero value smaller than that display precision keeps its significant digits so it cannot appear as zero. The stored and API values retain their original precision.

The current SvelteKit shell provides the responsive household dashboard, member and module administration navigation, account links, a keyboard-accessible mobile drawer and Quick Add empty state. Tracking has its own schema builder, quick-entry form and private measurement history. Other module landing screens remain placeholders until their domain issues add records and entry forms; Quick Add does not create or imply saved data on its own.

## Registry and permissions
Every module defines:
- Stable `module_key`, label and version.
- Optional integration dependencies and sensible standalone fallbacks.
- Backend provider, routes, policies, services, schema and queue integrations.
- SvelteKit routes/navigation, forms, empty/error states and responsive layouts.
- Capabilities (`view`, `create`, `edit`, `manage`) resolved against per-member grants.
- Explicit AI/MCP typed tool registration and required user confirmation for writes.
- Tests for enabled/disabled operation, private record ownership and data preservation.

A request is allowed only if module enabled **and** user has permission **and** target resource is visible. Enforce this at Laravel service/API/tool boundaries; UI state is advisory.

## Domains
- `tracking`: customizable fields, units, typed entries and chart history.
- `utilities`: multiple meters and readings, historical usage.
- `vehicles`: mileage, upkeep, insurance and costs.
- `finance`: income/outgoings, categories, budgets and recurring charges.
- `recipes`: recipes, ingredients, steps, categories and servings.
- `meal_planning`: weeks with meal slots, saved recipes or free-text meals.
- `pantry`: inventory quantities, storage, expiry and stock events.
- `shopping`: lists and independently manageable items.
- `analytics`, `import`: cross-cutting tools, gated by source-module permissions. The read-only assistant is a Core app feature and is not an optional module.
- `health` (future): private and separately consented data.

## Tracking module contract

Tracking supports private trackers owned by one member and household templates managed by an active administrator. A household template exposes its schema to members with Tracking `view` access; every measurement still belongs to its author and stays private unless the owner grants record-level access. Administrator status alone does not reveal private tracker definitions or measurements.

- `GET /api/tracking/trackers` lists definitions visible to the member and requires `view`.
- `POST /api/tracking/trackers` creates a private tracker with `create`, or a household template with active-admin status and exact `manage` access. A schema has 1–50 fields of type `number`, `text`, `date` or `boolean`.
- `GET /api/tracking/trackers/{tracker}` returns its schema and up to 20 immutable schema revisions; `PUT` updates the schema with exact `manage` access.
- `GET /api/tracking/trackers/{tracker}/entries` returns 30 visible entries by default, up to 50 per request, and requires `view`. Pass `before_recorded_at` and `before_id` from the last entry to load the next page without duplicates.
- Tracking history is ordered newest first by recorded date and entry ID. The web history loads the first 30 entries, then fetches older pages as the member scrolls; a keyboard-accessible load-more button remains available. The persistent app header links to tracker creation when the member has `create`, or is an active administrator with `manage` access. `TrackerSchemaService` rechecks active membership, module state and the exact capability in the creation transaction.
- `POST /api/tracking/trackers/{tracker}/entries` records an entry with exact `create` access. `PATCH /api/tracking/entries/{entry}` edits an accessible entry with exact `edit` access and ownership or an explicit record grant.
- `DELETE /api/tracking/trackers/{tracker}` removes a tracker and its entries with exact `manage` access. `DELETE /api/tracking/entries/{entry}` removes an accessible entry with exact `edit` access and ownership or an explicit record grant.

Numeric values are accepted as decimal strings, limited to 14 whole and 6 fractional digits, and persisted as `DECIMAL(20,6)`. Every numeric field requires an explicit unit. Values include label, type and unit snapshots so historical display survives field retirement. Once a field has values, its type and unit cannot change; replace it with a new field. Schema changes increment the version and append an immutable snapshot. Entry writes carrying a stale schema version return `409 Conflict` and require a reload.

## Utilities module contract

Utilities records cumulative electricity, gas and water meter values. Private meters are the default and belong to their creator. Only an active household administrator with exact Utilities `manage` access can create a household meter; its readings are shared with members who have the exact required module capability. Administrator status alone does not reveal a private meter, its readings, correction history or photos. A meter photo is stored on the API's private local disk, is never returned as a storage path or public URL, and is streamed only through an authenticated route after the same meter and reading `view` checks.

Meter type fixes the register unit: `electricity` uses `kWh`, `gas` and `water` use `m³`. Clients cannot submit an arbitrary unit or silently convert readings. Values and optional interval alert thresholds are non-negative decimal strings with at most 14 whole and 6 fractional digits, persisted as `DECIMAL(20,6)`. A reading date is unique per meter. Readings can be entered out of order only when the cumulative value remains between the immediately preceding and following chronological readings. Corrections may include an optional reason and append an immutable before/after revision in the same transaction. The meter row is locked before adjacent readings are checked and changed, so concurrent writes through the service cannot invalidate the ordering; the unique date index remains the database backstop.

Consumption is derived from the difference between adjacent visible readings; it is not stored separately. The API returns at most the latest 200 readings in chronological order, their derived interval consumption and elapsed days. If a member cannot view an adjacent private reading, the API does not calculate across that hidden value. An optional meter threshold marks an interval when its derived consumption is strictly greater than the configured amount; the warning is displayed in the meter history and trend chart. It is an interval warning, not a scheduled notification. Reading photos accept JPEG, PNG or WebP up to 5 MB and require Utilities `view` plus ownership or the exact record grant. Corrections and meter settings require exact `edit` or `manage` capability respectively; those capabilities do not imply `view`, `create` or each other.

The REST surface is `GET/POST /api/utilities/meters`, `GET/PATCH /api/utilities/meters/{meter}`, `POST /api/utilities/meters/{meter}/readings`, `PATCH /api/utilities/readings/{reading}`, and `GET /api/utilities/readings/{reading}/revisions` or `/photo`. Meter creation uses exact `create` for private meters and exact `manage` plus active-admin status for household meters. Every endpoint checks that Utilities is enabled and authorizes the exact module capability and resource at the service boundary.

## Vehicles module contract

Vehicles tracks a household fleet without making any record visible by default. Vehicles are private to their creator unless an active household administrator creates one with exact Vehicles `manage` access and chooses household visibility. Odometer readings, service records, insurance policies and costs inherit their vehicle's visibility. Administrator status alone never reveals a private vehicle or its history. Members still need the exact module capability and, for private records, an explicit resource grant for each accessed record.

Vehicles store make, model, optional model year, fuel type and a display name. The odometer unit is selected as `km` or `mi` and cannot be changed after any mileage is recorded. Odometer values are non-negative decimal strings with at most 17 whole and 3 fractional digits, stored as `DECIMAL(20,3)`. A vehicle has at most one odometer reading per date. Readings can be entered out of order only when the value remains between its adjacent chronological readings. Corrections may include an optional reason and append a before/after revision in the same transaction. A vehicle row lock serializes service writes; the unique date index remains the database backstop.

Maintenance records capture a service title, category, date, optional next due date, odometer value and note. Insurance records capture provider, coverage type and validity dates; the API derives active, upcoming or expired state. Vehicle costs store a non-negative amount as `DECIMAL(18,2)`, a three-letter uppercase currency code, a start date, an optional end date, and a period (`once`, `monthly`, `quarterly` or `yearly`). Period describes recurrence; no currency conversion or totals across different currencies are implied. Service, insurance and cost data remain private with their vehicle unless explicitly granted.

The REST surface is `GET/POST /api/vehicles`, `GET/PATCH /api/vehicles/{vehicle}`, `POST /api/vehicles/{vehicle}/odometer-readings`, `PATCH /api/vehicles/odometer-readings/{reading}`, `GET /api/vehicles/odometer-readings/{reading}/revisions`, and `POST /api/vehicles/{vehicle}/maintenance`, `/insurance` or `/costs`. Private vehicle creation uses exact `create`; household vehicle creation uses exact `manage` plus active-admin status. Odometer, maintenance, insurance and cost creation use exact `create`, corrections use exact `edit`, and vehicle detail changes use exact `manage`. Every operation checks that Vehicles is enabled and authorizes the caller and resource at the service boundary.

## Finance module contract

Finance tracks categorized income and expenses, monthly category budgets, and recurring entries without a banking connection. All records are private by default. An active household administrator can create a household category, transaction, budget, or recurring entry with exact Finance `manage` access. Admin status alone does not reveal another member's private records. Each operation requires the exact Finance capability and, for private records, ownership or a resource-level grant for the same operation.

Categories have a name and fixed type (`income` or `expense`). Names are unique without regard to case within the owner's private scope or the household scope. A transaction references a category of the same type, stores a positive amount as `DECIMAL(18,2)`, a three-letter uppercase currency code, description, optional payee up to 200 characters and occurrence date. Income and expense are separate types rather than signed input. The API accepts decimal strings with up to 16 whole and 2 fractional digits; it does not convert or combine different currencies. Category type cannot change after creation, and a category in use by a transaction, budget or recurring entry cannot be deleted.

Budgets set a positive monthly limit for one expense category and currency. `period_start` is the first day of the month; only one budget per category, month, currency and visibility owner is allowed. The overview groups income, expense and net totals by currency. Each budget shows spent and remaining amounts for its category and currency. A household budget counts only household-visible transactions so private member spending cannot influence a shared total; a private budget counts transactions the caller may view. No exchange rate or conversion is implied.

Recurring entries store a category, amount, currency, cadence (`weekly`, `monthly`, `quarterly` or `yearly`), start, next due date, optional end and active state. They do not create transactions automatically or run a background scheduler. `POST /api/finance/recurring/{entry}/record` explicitly records the current due occurrence as a transaction and advances the schedule in one database transaction. Repeating the same occurrence request is idempotent. Monthly and longer cadences retain the start date's day where possible and clamp to month end when needed.

Finance transaction import is part of the optional Import module and requires Import `create` plus Finance `view` and `create`. CSV files use a member-selected mapping for date, description, signed amount and ISO currency, with optional payee and category columns. Comma, semicolon and tab delimiters are detected from the header. Amounts accept a decimal point or comma without thousands separators; positive values become expenses and negative values become income. CAMT.053 XML entries use the booking date (or value date when booking date is absent), ISO currency and debit/credit indicator. Both formats are limited to 10 MB and 1,000 transactions. The preview reports malformed rows, inaccessible or ambiguous categories and duplicates without writing financial records. Members can select valid new rows while invalid rows remain visible for correction; each short-lived encrypted preview token is bound to the member, file digest, mapping, category defaults and selected rows. Confirmation requires `confirmed: true` and a UUID `Idempotency-Key`, rechecks module access and source data, and atomically creates only private transactions in the selected member's scope. Reusing an idempotency key returns the original result; a different key skips exact matches among the caller's visible transactions and prior imports. Duplicate fingerprints include payee, and duplicate checks never inspect other members' private transactions. Imported source references are retained only as one-way fingerprints for deduplication and are not included in transaction responses. No direct bank connection or currency conversion is performed.

The REST surface is `GET/POST /api/finance/categories`, `PATCH/DELETE /api/finance/categories/{category}`, `GET/POST /api/finance/transactions`, `PATCH/DELETE /api/finance/transactions/{transaction}`, `GET/POST /api/finance/recurring`, `PATCH/DELETE /api/finance/recurring/{entry}`, `POST /api/finance/recurring/{entry}/record`, `GET/POST /api/finance/budgets`, `PATCH/DELETE /api/finance/budgets/{budget}`, and `GET /api/finance/overview?month=YYYY-MM`. Transaction lists can filter by month and return at most 200 visible records. Optional Finance routes check module enablement, and typed service operations enforce exact capabilities, ownership and resource visibility.

## Recipes module contract

Recipes is an independently enabled module with no dependency on MealPlanning, Pantry or Shopping. It stores recipes with a title, optional free-text category, servings, optional preparation time, instructions, and an ordered list of ingredients. Ingredient quantities are positive exact decimal strings stored as `DECIMAL(14,4)` with an explicit member-supplied unit and optional note. Units are labels; the module does not silently convert them. Recipe photos are optional, limited to JPEG/PNG/WebP up to 5 MB, stored on the private local disk, and served only through an authenticated, resource-authorized route.

Recipes are private by default. Members with exact Recipes `create` can create private recipes and members with `edit` can change their own or explicitly shared private recipes. Only an active household administrator with `manage` can create or edit household recipes. Admin status alone does not reveal a private recipe. A resource-level permission must match the operation. Favorites are private to the signed-in member and require Recipes `view`; they do not grant access to recipe data.

The REST surface is `GET/POST /api/recipes`, `POST /api/recipes/import-preview`, `GET/PATCH/DELETE /api/recipes/{recipe}`, `PUT/DELETE /api/recipes/{recipe}/favorite` and `GET /api/recipes/{recipe}/photo`. Lists return up to 200 visible recipes and include ingredients, visibility, per-member favorite state and whether the current member may edit the recipe. `POST /api/recipes/import-preview` accepts either a public HTTPS `source_url` or a PDF upload up to 10 MB, plus the requested visibility. It returns editable recipe fields and warnings without saving. URL imports read Schema.org Recipe JSON-LD only, reject redirects and non-public DNS targets, pin the checked DNS addresses for the request, and cap response size and time. PDF imports extract selectable text from the first 20 pages; scanned PDFs are not supported. Imported page and PDF content are parsed locally and are not sent to an AI provider. Saving always uses the regular recipe endpoint and its existing authorization. Disabling Recipes blocks all API access while preserving recipes, ingredients, favorites and private photo files for later re-enablement. Recipes does not read or write meal plans, pantry stock or shopping lists.

## Meal Planning module contract

Meal Planning is independently enabled and requires only Core. `GET /api/meal-planning?week_start=YYYY-MM-DD` returns a Monday–Sunday week; the start date must be a Monday. `POST /api/meal-planning/slots`, `PATCH /api/meal-planning/slots/{slot}` and `DELETE /api/meal-planning/slots/{slot}` create, edit and remove one dated breakfast, lunch or dinner slot. Each slot accepts either a free-text dish name or an optional recipe reference, plus servings from 1 to 1,000 and an optional note. A unique household/member scope, date and meal type prevents duplicate slots for the same plan.

Plans are private to their creator by default and require the member's exact Meal Planning `view`, `create` and `edit` capability plus ownership or a matching resource-level grant. Only an active household administrator with exact `manage` can create or edit household-visible plans. Administrator status does not expose another member's private plan. Shared and private plan data remain stored while the module is disabled.

Free-text slots work when Recipes is disabled or unavailable to the member. Creating or changing a recipe reference requires Recipes to be enabled and the member to hold Recipes `view` plus visibility of that exact recipe. A plan response includes the linked title only after that same check; otherwise it returns a generic linked-recipe label without the recipe ID or private title. Deleting a recipe clears the optional reference and leaves the meal slot in place. Meal Planning never reads or changes pantry stock, creates shopping items, or changes saved recipe data. No pantry or shopping dependency is required.

## Pantry module contract

Pantry is independently enabled and requires only Core. `GET /api/pantry` returns up to 200 visible stock lines, ordered by best-before date, with optional `expiry=expired|today|soon|later|none` filtering; `soon` includes today through seven days ahead. `POST /api/pantry` creates a private stock line by default with a name, non-negative starting quantity, explicit unit label, optional storage location and optional best-before date. Only an active household administrator with exact Pantry `manage` can create household-visible stock. Quantities use `DECIMAL(14,3)` and are handled as exact decimal strings; units are labels and are not silently converted. A stock line's unit stays fixed so its movement history retains a consistent meaning.

`GET /api/pantry/{item}/movements` returns up to 200 authorized movements. Initial quantities above zero and every later manual change record before, delta, after, unit, optional note and timestamp. `POST /api/pantry/{item}/adjustments` accepts a signed `quantity_delta` and the loaded `expected_version`; it uses a row lock and increments the version. Stale edits return `409 Conflict`; a change that would make stock negative or exceed the supported decimal range is rejected. `PATCH /api/pantry/{item}` edits only the name, storage location and best-before date, also requiring `expected_version` so concurrent edits do not silently overwrite one another. No quantity changes happen through this metadata endpoint.

Stock lines are private to their creator by default and require exact Pantry `view`, `create` and `edit` capabilities plus ownership or a matching resource-level grant. Household-visible lines can be created or changed only by an active administrator with exact `manage`; members with `view` can see those lines and their movement history. Admin status does not reveal a member's private stock. The UI displays expired, today, and within-seven-day best-before states; it does not send notifications. Disabling Pantry blocks the API while preserving stock lines and history. Pantry does not depend on Recipes, Meal Planning or Shopping and does not change them.

## Shopping module contract

Shopping is independently enabled and requires only Core. `GET /api/shopping/lists` lists visible lists; `POST /api/shopping/lists` creates a private list by default. An active household administrator with exact Shopping `manage` may create a household list. `GET /api/shopping/lists/{list}` returns its visible items and capabilities. `PATCH /api/shopping/lists/{list}` renames a list with an expected version.

`POST /api/shopping/lists/{list}/items` adds an item with an optional positive decimal quantity and explicit unit; when a quantity is supplied its unit is required. Quantities use `DECIMAL(14,3)` and are returned as exact decimal strings. Units are labels and are never silently converted. `PATCH /api/shopping/items/{item}` edits item text, quantity, unit or order. `PATCH /api/shopping/items/{item}/checked` checks off or restores an item with an expected version; stale changes return `409 Conflict`. `POST /api/shopping/items/{item}/move` moves an item within its checked or unchecked group, and `DELETE /api/shopping/items/{item}` removes it while preserving its activity snapshot.

Lists are private to their creator by default; household lists are visible to members with Shopping `view`. Private list access follows ownership or an exact resource-level grant. Members with Shopping `create` can add items to lists they can access; members with Shopping `edit` can change, check, restore, reorder and remove items. An active administrator with Shopping `manage` can manage household lists. List activity is available through `GET /api/shopping/lists/{list}/history`, with before/after snapshots visible only to members who can view that list. Disabling Shopping blocks its API while preserving lists, items and history. Shopping has no Recipes, Meal Planning or Pantry dependency and does not write to those modules.

Optional meal-plan suggestions are available from a Shopping list through `POST /api/shopping/lists/{list}/meal-suggestions`. The endpoint previews one Monday–Sunday week and only uses plans and linked recipes the current member can view. Free-text meals and inaccessible recipe details do not expose ingredient data. Ingredient quantities are scaled to planned servings with exact decimal arithmetic; a result that cannot fit Shopping's three-decimal precision is skipped rather than rounded. Suggestions combine only matching normalized ingredient names and identical unit labels.

The preview can optionally read Pantry stock the member is authorized to view. It subtracts a quantity only when both the normalized ingredient name and unit label match exactly; it performs no unit conversion and never changes Pantry stock. If Meal Planning or Pantry is disabled or unavailable to the member, the preview degrades to no plan suggestions or full recipe quantities respectively. Adding suggestions requires a fresh preview, selected suggestion IDs and explicit `confirmed: true`; the API rechecks the source data, list version and Shopping permissions, then writes only the selected Shopping items. Stale proposals return `409 Conflict`. Re-enabling the optional modules restores their authorized integration without recreating or changing source data.

## Tasks module contract

Tasks is an optional module that depends only on Core. Tasks are private to their creator by default. A member with Tasks `create` can create a private task; only an active household administrator with exact Tasks `manage` can create, edit or delete a household task. Administrators still need the explicit module capability, and admin status alone does not grant access to private tasks. Every operation checks the module's enabled state, the exact capability and private-record visibility.

Tasks store a title, optional description, optional due timestamp and IANA timezone, priority (`low`, `medium`, `high`), optional active-member assignee, optional recurrence (`daily`, `weekly`, `monthly`, `yearly`) and an optimistic version. Repeating tasks require a due date and an interval from 1 to 99. A one-time task can omit its due date. Due timestamps are stored as UTC instants; recurrence advances the wall-clock time in the task timezone and preserves the local time across daylight-saving transitions. Monthly and yearly schedules retain the original calendar day after a month-end clamp: January 31 advances to February 28 and then March 31; a February 29 yearly schedule uses February 28 in non-leap years and returns to February 29 in leap years. Editing the due date, timezone or frequency establishes a new calendar anchor; changing only the interval keeps the existing anchor.

Private owners can assign another active member only when that member has Tasks `view` and `edit`, and the owner has exact Tasks `manage`; that assignment grants only the task's resource-level `view` and `edit`. The assignee can view and complete the task but cannot edit its details. A private owner can edit or complete their own task with exact Tasks `view` and `edit`. Household tasks are visible to members with Tasks `view`; the assigned member can complete with exact Tasks `view` and `edit`, while an active administrator can complete with exact Tasks `view`, `edit` and `manage`. Editing or deleting household tasks requires that administrator capability. Assignee choices are limited to active members with Tasks `view` and `edit` and are returned only to members with Tasks `manage`.

`GET /api/tasks` returns up to 200 authorized tasks and supports `status=open|completed|all`, `priority=low|medium|high`, `due=overdue|upcoming|none`, an optional assignee filter, and sorting by due date, priority, assignee or creation time. The web filter offers assignees present in the member's authorized task results; `GET /api/tasks/assignees` returns all eligible assignees only to members with exact Tasks `manage`. `POST /api/tasks` creates a task; `PATCH /api/tasks/{task}` edits an owned private or managed household task with `expected_version`; `DELETE /api/tasks/{task}` removes the same authorized records and their completion history. `POST /api/tasks/{task}/complete` requires the current version and records the actor and completion time. Stale or duplicate completion attempts return `409 Conflict`.

Each completion is stored with its occurrence number. Completing a one-time task marks it complete. Completing a recurring task advances the due date, increments the occurrence number and opens the next occurrence in the same transaction; a unique `(task, occurrence)` key prevents duplicate history. `GET /api/tasks/{task}/history` returns up to 100 completion records only to members currently authorized to view the task. Disabling Tasks blocks its API and navigation while preserving tasks and their history.

## Analytics module contract

Analytics is optional, depends only on Core and stores each member's dashboard widgets privately. `GET /api/analytics/catalog` lists only metrics whose source module is enabled and for which that member has exact `view` access. `GET /api/analytics/dashboard` returns the member's widgets and recomputes their data using current source-module and record-level permissions. A widget whose source becomes disabled or unavailable remains in its owner's configuration but returns no periods or values until access is restored.

The first metric catalog contains Finance expenses, Utilities consumption and Vehicles distance. Finance values are grouped by currency, utility consumption by the meter's unchanged unit label, and distance by the vehicle's unchanged odometer unit. No exchange rates or unit conversions are applied. Time ranges are trailing 30 days grouped by day, trailing 90 days grouped by week, or the current and preceding 11 calendar months grouped by month. Consumption and distance are differences between adjacent visible readings; a hidden reading breaks the interval so Analytics never calculates across an inaccessible value.

Members with Analytics `create` can add up to 12 private widgets with a custom title, time range and line or bar chart. Members with exact `edit` can update or remove their own widgets; an expected version prevents stale concurrent edits. The API is `GET /api/analytics/catalog`, `GET /api/analytics/dashboard`, `POST /api/analytics/widgets`, `PATCH /api/analytics/widgets/{widget}` and `DELETE /api/analytics/widgets/{widget}`. Source queries aggregate only visible records and never return descriptions, notes, photos or other source fields. Disabling Analytics preserves widget configuration; disabling a source module preserves its data and hides its values from Analytics.

## Import module contract

Import is optional and depends only on Core. Utility readings support CSV import/export; Finance transactions support CSV and CAMT.053 import. Each workflow additionally requires its source module to be enabled and the caller to hold the source module's exact capabilities. `GET /api/import/utilities/meters/{meter}/readings.csv` exports only readings visible to the caller. An export needs Import and Utilities `view` capability plus visibility of the selected meter and each returned reading. Notes that begin with spreadsheet formula characters are escaped in the exported file.

`POST /api/import/utilities/meters/{meter}/readings/preview` first inspects a UTF-8 CSV header with 2–100 columns and returns common-name mapping suggestions. The caller maps a date and value column plus an optional note column; the server then validates up to 1,000 data rows and a 10 MB file. Dates use `YYYY-MM-DD`; values are non-negative decimal strings with up to 14 whole and 6 fractional digits. A mapped preview returns row errors, identical existing rows to skip, and a short-lived encrypted token bound to the caller, meter, file digest and column mapping. It writes no readings. `POST /api/import/utilities/meters/{meter}/readings/confirm` requires that token, the same mapping, `confirmed: true` and a UUID `Idempotency-Key`. The server revalidates the file and current permissions, then creates valid rows in one transaction. The same key and file mapping return the original result; reimports with a new key skip identical meter/date/value/note records, while conflicting rows are rejected. A source meter with any reading hidden from the caller cannot be imported because chronology validation must not inspect inaccessible values.

`POST /api/import/utilities/meters/{meter}/reading-suggestions` runs local Tesseract OCR on an uploaded meter photo and returns at most one unambiguous decimal suggestion. Images are processed from the request temporary file and are not stored by this operation or sent to an AI provider. A suggestion is never persisted by OCR; the user must verify it and submit the existing Utilities reading form. It requires Import and Utilities `create` and `view` access plus visibility of the meter. The API image uses the open-source Tesseract engine and English recognition data; if local OCR is unavailable, manual entry remains available.

Disabling Import blocks its import, export and OCR routes without deleting existing module data or completed readings. Disabling Utilities also blocks these workflows and preserves its records and private photos. No external AI provider or cloud service is required.

`POST /api/import/finance/transactions/preview` inspects a CSV header or parses a CAMT.053 XML statement, validates rows and returns accessible Finance categories for mapping. CSV columns map date, description, amount and currency; payee and category columns are optional. Comma, semicolon and tab delimiters are detected from the header. Amounts accept a decimal point or comma without thousands separators; expenses use positive values and income uses negative values. CAMT.053 uses debit and credit indicators. Valid rows default to selected, and the member can deselect rows before refreshing the preview. Categories must be visible to the caller with Finance `create`; a mapped category name must identify exactly one category of the corresponding transaction type. Duplicate matching checks only the caller's visible Finance transactions and the caller's prior imports, and fingerprints include the optional payee. Unknown, ambiguous or inaccessible categories are reported as row errors, not silently reassigned. `POST /api/import/finance/transactions/confirm` accepts the encrypted preview token, the selected row numbers, `confirmed: true` and a UUID `Idempotency-Key`. Confirmation writes selected transactions in one transaction, applies the existing positive decimal/currency rules, stores payee on each transaction and records import fingerprints without storing raw statement files. Existing transactions have a null payee until updated. Repeated confirmation with the same key is idempotent; a new key skips already imported matches. No bank credentials, third-party providers or automatic account synchronization are part of this workflow.

## AI read-only assistant

The read-only household assistant is part of Core and opens from the app shell with `⌘K` (or `Ctrl+K`). `GET /api/ai/assistant` reports provider availability and the data tools currently available to the signed-in member. `POST /api/ai/assistant` accepts one question (up to 4,000 characters) and returns an answer without storing chat history. Active members can use it without a separate AI module grant. Every tool is registered by the server, is offered only when its source module is enabled and the member has exact `view`, and calls the existing domain service again at execution time. Those services recheck record ownership or resource-level grants, so the assistant can use household-visible data and the member's own or explicitly shared private data only. Current tools cover Finance, Tracking, Utilities, Vehicles, Recipes, Meal Planning, Pantry, Shopping and Analytics. Results are bounded; the assistant has no write, SQL or shell tools.

The provider defaults to disabled. An active administrator configures it under **General settings**; the API key is encrypted in household settings and is never returned to the browser. Administrators can select an OpenAI-compatible endpoint, Anthropic Claude, Google Gemini or OpenRouter and set the model and provider key. OpenAI-compatible endpoints can be local or hosted; the branded providers use their managed HTTPS endpoints. Every hosted-provider request requires the signed-in member to explicitly confirm sending their question and any authorized tool data to that provider. Provider failures are returned without logging prompts, tool results or credentials. Environment configuration remains available as a deployment fallback.

Claude and Gemini use their native tool-call formats, while OpenRouter uses its OpenAI-compatible chat completions API. All providers receive only the registered read-only tools available to the member; the application executes those tools and rechecks permissions. A provider change clears the previously stored API key, so an administrator must supply a key for the newly selected provider.

Members can save private user-wide or project-key context at `/api/ai/context`. A project key is a member-owned grouping label, not a shared household project or authorization grant. Every context operation is scoped to the authenticated owner. The assistant includes at most ten relevant, unexpired entries and 4,000 characters, selected by question terms and recency. Context is tagged as untrusted data and never establishes permissions or instructions. Each entry records its type, optional source, timestamps, optimistic version and expiry. `AI_CONTEXT_RETENTION_DAYS` defaults to 365 days; the hourly `metricove:purge-ai-context` task removes expired entries. Members can disable context use without deleting records, export their entries through the list endpoint, or delete entries individually.

## MCP external access

`POST /api/mcp` serves the official PHP MCP SDK's stateless HTTP lifecycle. It accepts Metricove user-managed bearer tokens created in the member's profile, not OAuth access tokens. Metricove does not provide OAuth authorization-server discovery or an OAuth grant flow; clients must support the stateless MCP protocol exposed by the installed SDK. The optional `MCP_ALLOWED_ORIGINS` environment value is a comma-separated list of additional browser origins. Host validation remains tied to `APP_URL` and local development hosts.

Active members can open the MCP connection and tool reference at `/mcp-docs`. The Laravel OpenAPI reference is generated by Scramble at `/docs/api` with its JSON document at `/docs/api.json`; both routes require an authenticated active-member session. OpenAPI documents Laravel HTTP routes, while the available MCP tools are negotiated through the MCP `tools/list` method and are documented on `/mcp-docs`.

Token scopes are limited to `tracking:view`, `finance:view`, `utilities:view`, `utilities:create` and `vehicles:view`, and are offered only when that member currently has the matching enabled-module permission. Every request recomputes current grants; a token never grants access on its own. The existing read tools return bounded, typed summaries and call their domain services again, preserving private-record visibility. The MCP endpoint has a per-IP rate limit; token secrets and action payloads are not written to logs or audit details.

The only MCP write tool currently implemented is `preview_utility_reading`, followed by `complete_approved_utility_reading`. A preview is encrypted at rest, expires after ten minutes and changes no utility data. The owning member must review the meter, date, value and note in `/profile` and approve or reject it using the authenticated session and CSRF protection. Completion requires the same live token, current Utilities view/create access, a fresh resource-visibility and chronology check, and a UUID idempotency key. Repeating a completed action with that same key returns the minimal original result; a different key cannot replay the action. Revoking the token, suspending the member or disabling Utilities prevents approval/completion immediately. Token lifecycle and action preview/approval/rejection/execution are audited with identifiers and scope metadata only.

## Cross-module rule
A shared integration must not make an optional module mandatory. Shopping works when Recipes, Pantry and Meal Planning are disabled. Meal Planning supports free-text dishes. Disabled or inaccessible sources degrade gracefully, and re-enabling restores only authorized integration access without deleting data.
